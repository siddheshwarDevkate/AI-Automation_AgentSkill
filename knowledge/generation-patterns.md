# GENERATION PATTERNS

## Purpose
Reusable code generation patterns for common web application UI components, so pages are generated by recognizing patterns rather than from scratch element-by-element. Refer to framework-rules.md, framework-architecture.md, playwright-best-practices.md, and locator-strategy.md alongside this file.

## Used By Skills
All 8 skills (01–08)

## Objective
Generate automation by recognizing UI patterns. Whenever a familiar pattern is detected, follow its corresponding generation strategy instead of a bespoke implementation.

## Pattern Detection Strategy

**Step 1 — Analyze the Application.** Use the configured browser automation tool (Playwright MCP) to launch, authenticate, navigate every accessible page/menu/dialog, and inspect the DOM. The live application is the single source of truth — never assume.

**Step 2 — Identify the Page Type.** Login, Dashboard, Search, CRUD, Form, Settings, Profile, Reports, Wizard, Administration. A page may belong to more than one category.

**Step 3 — Detect UI Components.** Forms, tables, search panels, filters, dropdowns, checkboxes, radio buttons, date pickers, file upload controls, modal dialogs, toast messages, side navigation, pagination, tabs, accordions, cards.

**Step 4 — Match Generation Patterns.** e.g. Login Page → Login Pattern; Search Page → Search Pattern; Data Table → Table Pattern; Modal Dialog → Modal Pattern; Pagination → Pagination Pattern.

**Step 5 — Combine Multiple Patterns.** Most enterprise pages contain several patterns — don't pick just one. Example: an Employee Management page combining Search + Data Table + CRUD + Pagination + Dialog patterns should generate one cohesive Page Object applying all of them together.

**Step 6 — Validate Pattern Selection.** Before generating code, verify every major page was analyzed, all interactive components identified, correct patterns selected, nothing important missed, and the selected patterns accurately represent the application's behaviour.

## Generation Workflow
Analyze the application → identify page type → detect reusable UI patterns → apply matching pattern(s) → generate Page Object → generate Test Specification → validate implementation.

## Pattern Library

**1. Login Page** — username/password fields, login button, error message, remember-me/forgot-password (optional). Methods: `fillUsername()`, `fillPassword()`, `clickLoginButton()`, `performLogin()`, `verifyLoginPageVisible()`, `verifyErrorMessageVisible()`, `verifyCurrentUrl()`, `verifyPageTitle()`. Tests: valid login, invalid username/password, empty credentials, locked user (if supported).

**2. Search Page** — search box, search/clear buttons, results, filters. Methods: `fillSearch()`, `clickSearch()`, `clearSearch()`, `performSearch()`, `verifySearchResults()`, `verifyNoResultsMessage()`. Tests: valid/invalid keyword, empty search, special characters, clear search.

**3. CRUD Page** — Add/Edit/Delete/Save/Cancel, data table. Methods: `clickAdd()`, `fillForm()`, `clickSave()`, `clickEdit()`, `clickDelete()`, `verifyRecordCreated()`, `verifyRecordUpdated()`, `verifyRecordDeleted()`. Tests: create/update/delete record, cancel operation, duplicate record.

**4. Form Page** — multiple inputs (textboxes, dropdowns, radio, checkbox, date pickers). Generate a dedicated method per field rather than one large `fillForm()` unless repeatedly reused. e.g. `fillFirstName()`, `selectCountry()`, `selectGender()`, `clickSubmit()`.

**5. Data Table** — rows, columns, pagination, sorting, filtering. Methods: `verifyTableVisible()`, `getRowCount()`, `getColumnCount()`, `clickRow()`, `verifyRowExists()`, `verifyCellValue()`. Tests: verify records, sort, filter, pagination, empty table.

**6. Sidebar/Navigation** — hamburger menu, sidebar, drawer, left nav. Always: open menu → wait for menu → click target item → verify destination page. Never click hidden navigation items.

**7. Modal Dialog** — popup, confirmation, alert, modal window. Methods: `verifyDialogVisible()`, `clickConfirm()`, `clickCancel()`, `closeDialog()`. Tests: open/close dialog, confirm/cancel action.

**8. File Upload** — upload button, choose file, drop zone, attachment. Methods: `uploadFile()`, `verifyUploadSuccess()`, `removeUploadedFile()`. Tests: valid/invalid file, large file, unsupported format.

**9. Dropdown** — `selectOption()`, `verifySelectedOption()`. Tests: select valid/invalid/default option.

**10. Checkbox** — `check()`, `uncheck()`, `verifyChecked()`, `verifyUnchecked()`.

**11. Radio Button** — `selectOption()`, `verifyOptionSelected()`.

**12. Date Picker** — `selectDate()`, `clearDate()`, `verifyDate()`.

**13. Toast Message** — `verifySuccessMessage()`, `verifyErrorMessage()`, `verifyWarningMessage()`.

**14. Pagination** — `goToNextPage()`, `goToPreviousPage()`, `goToPage()`, `verifyCurrentPage()`.

**15. Logout** — `clickLogoutButton()`, `performLogout()`, `verifyLogoutSuccessful()`. If logout is inside a hidden menu: open menu → wait → click logout → verify login page.

## Generation Decision Tree
Analyze Page → Identify Page Type → Recognize UI Pattern → Apply Matching Pattern → Generate Methods → Generate Tests → Validate Against Framework Rules → Return Final Code

## Reuse Strategy
Before generating new methods, always check: can an existing method be reused? Can multiple actions be combined into a reusable business method? Can common logic move to BasePage or a Helper? Avoid duplicate implementations.

## When No Pattern Matches
Analyze the page structure, identify reusable components, generate methods following framework conventions, maintain naming consistency, follow all framework standards. Do not force a page into an incorrect pattern.

## Final Checklist
✓ Correct pattern selected · ✓ methods follow naming conventions · ✓ no duplicate implementations · ✓ business logic inside Page Objects · ✓ tests cover expected scenarios · ✓ pattern applied consistently · ✓ framework rules followed · ✓ output matches templates
