# GENERATION PATTERNS

## Purpose
Reusable code generation patterns for common web application UI components, so pages are generated by recognizing patterns rather than from scratch element-by-element. Refer to .claude/skills/knowledge/framework-rules.md, .claude/skills/knowledge/framework-architecture.md, .claude/skills/knowledge/playwright-best-practices.md, and .claude/skills/knowledge/locator-strategy.md alongside this file.

## Dependency Matrix
Which Skills load this file is declared in .claude/agent/agent.md's Skill Dependency Matrix — that table is the single source of truth. Its primary consumers are Skills 02, 03, 04, and 07; the rest reference the Pattern Library for naming/reuse consistency only.

## Objective
Generate automation by recognizing UI patterns. Whenever a familiar pattern is detected, follow its corresponding generation strategy instead of a bespoke implementation.

## Pattern Detection Strategy

**Step 1 — Analyze the Application.** Use the configured browser automation tool (Playwright MCP) to launch, authenticate, and navigate the pages/menus/dialogs referenced by the parsed Test Case Model, inspecting the DOM along the way. The live application is the single source of truth for behaviour — never assume — but the Test Case Model is the source of truth for scope: don't free-crawl pages no test case touches.

**Step 2 — Identify the Page Type.** Login, Dashboard, Search, CRUD, Form, Settings, Profile, Reports, Wizard, Administration. A page may belong to more than one category.

**Step 3 — Detect UI Components.** Forms, tables, search panels, filters, dropdowns, checkboxes, radio buttons, date pickers, file upload controls, modal dialogs, toast messages, side navigation, pagination, tabs, accordions, cards.

**Step 4 — Match Generation Patterns.** e.g. Login Page → Login Pattern; Search Page → Search Pattern; Data Table → Table Pattern; Modal Dialog → Modal Pattern; Pagination → Pagination Pattern.

**Step 5 — Combine Multiple Patterns (mandatory, not optional).** Most enterprise pages contain several patterns — don't pick just one, and never give any of them their own class. Example: an Employee Management page combining Search + Data Table + CRUD + Pagination + Dialog patterns must generate exactly one cohesive `EmployeeManagementPage.ts` applying all of them together as methods — never `SearchPage.ts` + `DataTablePage.ts` + `PaginationPage.ts` as separate files for what is a single page.

**Step 6 — Validate Pattern Selection.** Before generating code, verify every major page was analyzed, all interactive components identified, correct patterns selected, nothing important missed, and the selected patterns accurately represent the application's behaviour.

## Generation Workflow
Analyze the application → identify page type → detect reusable UI patterns → apply matching pattern(s) → generate Page Object → generate Test Specification → validate implementation.

## Pattern Library

**Critical distinction — every entry below describes METHODS to add to the Page Object of the page it appears on. Not one of these entries is ever a Page Object in its own right.** Patterns 1–4 happen to be marked "(page-level)" because they typically describe an entire page's purpose — but even then, the pattern still produces methods on that single page's class, not a new class named after the pattern. Patterns 5, 7, 9–14 are "(component-level)": they describe a widget that lives inside a page (often alongside other components on the same page) and must fold into that page's existing Page Object. See .claude/skills/knowledge/framework-architecture.md's Page vs Component distinction and .claude/skills/skill-04-page-object-generation.md's Page Object Count Rule — the number of Page Objects always equals Skill 02's Page Inventory count, never the number of patterns detected.

**1. Login Page (page-level)** — username/password fields, login button, error message, remember-me/forgot-password (optional). Methods: `fillUsername()`, `fillPassword()`, `clickLoginButton()`, `performLogin()`, `verifyLoginPageVisible()`, `verifyErrorMessageVisible()`, `verifyCurrentUrl()`, `verifyPageTitle()`. Tests: valid login, invalid username/password, empty credentials, locked user (if supported).

**2. Search Page (page-level)** — search box, search/clear buttons, results, filters. Methods: `fillSearch()`, `clickSearch()`, `clearSearch()`, `performSearch()`, `verifySearchResults()`, `verifyNoResultsMessage()`. Tests: valid/invalid keyword, empty search, special characters, clear search.

**3. CRUD Page (page-level)** — Add/Edit/Delete/Save/Cancel, data table. Methods: `clickAdd()`, `fillForm()`, `clickSave()`, `clickEdit()`, `clickDelete()`, `verifyRecordCreated()`, `verifyRecordUpdated()`, `verifyRecordDeleted()`. Tests: create/update/delete record, cancel operation, duplicate record.

**4. Form Page (page-level)** — multiple inputs (textboxes, dropdowns, radio, checkbox, date pickers). Generate a dedicated method per field rather than one large `fillForm()` unless repeatedly reused. e.g. `fillFirstName()`, `selectCountry()`, `selectGender()`, `clickSubmit()`.

**5. Data Table (component-level — fold into the containing page)** — rows, columns, pagination, sorting, filtering. Methods: `verifyTableVisible()`, `getRowCount()`, `getColumnCount()`, `clickRow()`, `verifyRowExists()`, `verifyCellValue()`. Tests: verify records, sort, filter, pagination, empty table. Example: a Reports page with a data table gets these methods added directly to `ReportsPage.ts` — never a separate `DataTablePage.ts`.

**6. Sidebar/Navigation (cross-page — usually lives in BasePage or a shared component)** — hamburger menu, sidebar, drawer, left nav. Always: open menu → wait for menu → click target item → verify destination page. Never click hidden navigation items.

**7. Modal Dialog (component-level — fold into the containing page)** — popup, confirmation, alert, modal window. Methods: `verifyDialogVisible()`, `clickConfirm()`, `clickCancel()`, `closeDialog()`. Tests: open/close dialog, confirm/cancel action.

**8. File Upload (component-level — fold into the containing page)** — upload button, choose file, drop zone, attachment. Methods: `uploadFile()`, `verifyUploadSuccess()`, `removeUploadedFile()`. Tests: valid/invalid file, large file, unsupported format.

**9. Dropdown (component-level — fold into the containing page)** — `selectOption()`, `verifySelectedOption()`. Tests: select valid/invalid/default option. A column-selection dropdown on a Reports page becomes `selectColumns()` on `ReportsPage.ts`, never `ColumnSelectionPage.ts`.

**10. Checkbox (component-level — fold into the containing page)** — `check()`, `uncheck()`, `verifyChecked()`, `verifyUnchecked()`.

**11. Radio Button (component-level — fold into the containing page)** — `selectOption()`, `verifyOptionSelected()`.

**12. Date Picker (component-level — fold into the containing page)** — `selectDate()`, `clearDate()`, `verifyDate()`.

**13. Toast Message (component-level — fold into the containing page)** — `verifySuccessMessage()`, `verifyErrorMessage()`, `verifyWarningMessage()`.

**14. Pagination (component-level — fold into the containing page)** — `goToNextPage()`, `goToPreviousPage()`, `goToPage()`, `verifyCurrentPage()`.

**15. Logout (action — fold into the containing page or BasePage)** — `clickLogoutButton()`, `performLogout()`, `verifyLogoutSuccessful()`. If logout is inside a hidden menu: open menu → wait → click logout → verify login page.

## Generation Decision Tree
Analyze Page → Identify Page Type → Recognize UI Pattern → Apply Matching Pattern → Generate Methods → Generate Tests → Validate Against Framework Rules → Return Final Code

## Reuse Strategy
Before generating new methods, always check: can an existing method be reused? Can multiple actions be combined into a reusable business method? Can common logic move to BasePage or a Helper? Avoid duplicate implementations.

## When No Pattern Matches
Analyze the page structure, identify reusable components, generate methods following framework conventions, maintain naming consistency, follow all framework standards. Do not force a page into an incorrect pattern.

## Final Checklist
✓ Correct pattern selected · ✓ every detected pattern folded into its containing page's Page Object, never given its own class · ✓ methods follow naming conventions · ✓ no duplicate implementations · ✓ business logic inside Page Objects · ✓ tests cover expected scenarios · ✓ pattern applied consistently · ✓ framework rules followed · ✓ output matches templates
